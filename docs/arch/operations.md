# Публичный сайт, админка и разработка с DeepSeek

> С 06.11.2026 источник и CI — **Gitea** (`http://10.77.0.1/`, SSH `10.77.0.1:2222`,
> Actions). Упоминания GitLab ниже относятся к прежней инфраструктуре и оставлены
> как история миграции.

Задача Gitea #1, владелец niktar411. Работа ведётся в отдельной рабочей копии;
исходный каталог OneDrive не изменяется.

## Два сервера

**Сервер 1 — публичный.** Docker Compose `docker-compose.yml`:

- `web` — nginx со статической сборкой SolidJS, публичные 80/443;
- `api` — Go (chi + huma), миграции goose, PostgreSQL через pgx, статика и SEO;
- `postgres` — PostgreSQL 18, порт не публикуется;
- `gitea` — Gitea, доступна только на VPN-адресе `10.77.0.1`:
  `http://10.77.0.1/`, SSH — `10.77.0.1:2222`. Репозиторий:
  `ssh://git@10.77.0.1:2222/hackathon/hackathon.git`. Адрес в `GITLAB_URL`
  указывает на `http://10.77.0.1`, а `GIT_PROVIDER=gitea`;
- `gitea-runner` — act_runner, исполняет Gitea Actions;
- `orchestrator` — внутренний релей к воркеру второго сервера, наружу не публикуется;
- агент `hackathon-agent` — ограниченные операции и метрики на `10.77.0.1:9101`.

**Сервер 2 — только VPN.** Docker Compose `docker-compose.worker.yml`:

- `worker-agent` — HTTPS-подобный JSON API на `10.77.0.10:9102`, принимает запросы
  только с `10.77.0.1` и только с общим секретом;
- `coding-image` — образ с инструментами и проверками;
- `postgres-image` — образ для временных БД;
- `review` — просмотр сборки на `10.77.0.10:8080`, только из VPN.

Публичных портов у второго сервера нет. Исходящий трафик разрешён только на
первый сервер (`deploy/nftables-worker.sh`, `deploy/ufw-worker.sh`). Ссылки на
review выдаются только администратору через VPN.

## Граница доступа

Публичный сайт, страница вопросов и планировщик доступны без регистрации.
Планировщик публикуется на отдельном адресе `PLANNER_BASE_URL`; домен не зашит
в код и задаётся конфигурацией.

Администратор входит по локальному имени и паролю на `/admin`. Сервер требует
одновременно: локальную сессию (`AuthKind=local`), роль `admin`, точное имя
`ADMIN_USERNAME` и один из адресов списка `ADMIN_VPN_IP` (через запятую).
Проверка адреса выполняется по реальному соединению. За внутренним nginx
адрес берётся из `X-Real-IP`, который nginx перезаписывает; клиентский
`X-Forwarded-For` напрямую не принимается.
Статус администратора GitLab сам по себе доступа не даёт. Пароли хранятся как
Argon2id, сессии — как SHA-256-хеши непрозрачных токенов в HttpOnly-cookie,
изменяющие запросы требуют проверенного Origin и CSRF-заголовка.

Участники разработки входят на `/coding` локальными аккаунтами. Аккаунт можно
отключить; отключение и сброс сессий немедленно прекращают доступ. Старый вход
через GitLab OAuth остаётся только для прежнего командного чата и не может
выдать администратора.

## Чат на `ai.cool-domain.online`

`ai.cool-domain.online` отдаёт собственный интерфейс команды: `/` перенаправляет
на `/chat`, `/api/` проксируется в API. `/chat` на публичном и planner-хостах
открывает тот же экран внутри SPA.

- `POST /api/chat/stream` — SSE-поток ответа: события `meta`, `reasoning`,
  `content`, `done`, `error`. Рассуждения приходят из `reasoning_content`
  и показываются в анимированном блоке «Модель думает…»; итоговый ответ
  сохраняется в `messages`, как у обычного `POST /api/chat`.
- для этого адреса nginx использует `client/snippets/proxy-stream.conf`:
  `proxy_buffering off`, `proxy_read_timeout 3600s`; общий `proxy.conf`
  с `proxy_buffering on` здесь не подключается.
- `POST /api/chat` остаётся для нестриминговых клиентов и тестов.

### Контекст и уточнения

- Системный промпт собирается из базового правила фазы, общего доступа
  (сервер, репозиторий, деплой), `AGENTS.md` с сервера, общего контекста из
  админки и персонального контекста участника.
- `AGENTS.md` читается из `/app/AGENTS.md` (bind mount `./AGENTS.md:ro`);
  изменения подхватываются следующим запросом без перезапуска API.
- Общий контекст хранится в `application_settings.chat_general_context`
  и редактируется во вкладке «Контекст ИИ» админки
  (`GET/PUT /api/admin/chat-context`). Персональный контекст участника
  редактируется отдельно во вкладке «Контексты».
- Уточняющие вопросы задаются один раз: на второе сообщение фаза
  `clarifying` автоматически переходит в `ready`. Фраза
  «продолжи работу на свое усмотрение» пропускает уточнение сразу.

Внутренний контейнер OpenCode сохранён, но больше не публикуется на домене:
он слушает только `127.0.0.1:4096`. Его детали:

- контейнер `hackathon-opencode` собран из `deploy/opencode/Dockerfile`;
- вход через nginx Basic auth обычными локальными аккаунтами (`niktar411`,
  `egor`, `leonid`, `igor`); OpenCode получает внутреннюю авторизацию через
  заголовок, который подставляет nginx;
- пароли и хеши: `/etc/hackathon/opencode-users.txt` (временно, 0600),
  `/etc/hackathon/opencode.htpasswd`; внутренний пароль OpenCode —
  `/etc/hackathon/opencode.env` (0600);
- проект по умолчанию — `/hackathon` внутри контейнера, сессия «Хакатон»;
- рабочее дерево — отдельный клон `/srv/opencode/workspace`, внутри контейнера
  смонтирован как `/hackathon` (так проект называется в UI); git-remote удалён,
  агент не может напрямую пушить в production-репозиторий;
- конфигурация `/srv/opencode/config/opencode.json` разрешает только
  `opencode-go/deepseek-v4.1-flash`;
- у контейнера нет Docker-сокета; лимиты `1 CPU / 1200 MiB`.

Установка и обновление: `sudo sh deploy/opencode/install.sh`.

## Публичные данные

- `GET /api/public/site-config` — адреса сайта и планировщика и проверенные ссылки;
- `POST /api/public/questions` — ответ DeepSeek строго по контексту, который
  редактирует администратор; вопрос передаётся модели как недоверенный блок,
  типовые prompt-injection фразы отклоняются до вызова модели, а ответ проверяется
  на безопасный plain text; модель выбирает ссылки только из серверного реестра,
  произвольные URL отбрасываются; есть ограничение частоты;
- `GET /api/public/planner` — блоки плана; прогресс (`pipelineStatus`, approvals,
  состояние MR) сервер получает из GitLab и не принимает от клиента.

Создавать и менять блоки плана может только администратор или его AI-инструмент
в подтверждённой задаче. Владелец блока может отметить его как «выполняется»
через `POST /api/planner/blocks/{id}/start`; тот же переход делает coding-агент
инструментом `start_planner_block`, когда начинает работу над своим блоком.
Ручная отметка хранится в `planner_blocks.started_at` и даёт состояние
`verifying`, пока GitLab не сообщит более точный прогресс. Публичный клиент
не получает кнопок изменения.

## Разработка с DeepSeek

1. Участник создаёт задачу. Сервер всегда сначала задаёт 1–3 уточняющих вопроса.
2. Работа начинается только после явного подтверждения пользователем.
3. Воркер второго сервера готовит изолированное рабочее дерево и выдаёт модели
   только фиксированные инструменты: список/чтение/поиск/запись файлов, проверки,
   создание Merge Request. Произвольные команды недоступны.
4. Секреты, `.env`, ключи, `.git`, выход за рабочее дерево и симлинки запрещены
   на уровне воркера (`server/internal/infra/worker/security.go`).
5. Проверки — только из фиксированного набора (`bun-check`, `client-build`,
   `server-test`, `server-vet`) в контейнере без сети, кроме временной БД;
   результат каждой проверки сохраняется в аудите задачи.
6. Merge Request создаётся в защищённую ветку. Прямой push в `main` запрещён;
   слияние возможно только при зелёном CI, совпадении SHA и подтверждении
   администратора. Вебхук GitLab после слияния запускает развёртывание и проверку.

Доработка оформляется новой задачей со ссылкой на родительскую и снова проходит
уточнение и подтверждение.

## Ограниченные операции

Агент выполняет только заранее известные действия: `deploy`, `rollback`,
`restart`, `start`, `stop`, `create_test_database`, `drop_test_database` с
фиксированными аргументами. Произвольного shell нет.

Для рабочего окружения production-действия идут через `Production`
(`server/internal/infra/ops/production.go`): перед изменением создаётся дамп PostgreSQL и
копия compose-файла, после запуска проверяется health-check, при неуспехе
выполняется откат к предыдущему релизу и восстановление БД. Для сервера 2
операции ограничены `coding`, `review`, `test`; временная БД создаётся с
одноразовым паролем и удаляется после проверки.

AI может запускать, останавливать и перезапускать контейнеры и временные БД,
включая production, но только этими инструментами: с лимитами, аудитом,
резервной копией, health-check и откатом. Прямой `deploy` в production из AI
запрещён — только через подтверждённый Merge Request.

## Учёт DeepSeek

Запросы выполняются сервером через OpenAI-совместимый endpoint OpenCode Go
(`https://opencode.ai/inference/go/openai/v1`) или Cloud.ru. Разрешена ровно одна
модель — **DeepSeek V4.1 Flash**; `validateModelEndpoint` не даёт запустить сервер
с другим именем модели или чужим HTTPS-хостом. Ключ хранится зашифрованным
(AES-GCM, `SETTINGS_ENCRYPTION_KEY`) и может быть заменён в админке; браузеру он
не передаётся. Сохраняются usage, модель, пользователь, время и результат.
Отсутствующий usage означает неизвестный расход, а не ноль.

## Зеркало GitHub

GitLab остаётся основным репозиторием; GitHub — только зеркало
`niktar411/hakaton-14-11-2026`. Зеркалирование запускается на первом сервере,
потому что исходящий трафик второго сервера ограничен первым.

```
/etc/hackathon/mirror.env   0600
  GITLAB_REPOSITORY=ssh://git@10.77.0.1:2222/hackathon/hackathon.git
  GITLAB_SSH_KEY=/etc/hackathon/mirror/id_ed25519
  GITHUB_REPOSITORY=niktar411/hakaton-14-11-2026
  GITHUB_MIRROR_TOKEN=<fine-grained token, Contents: read and write>
```

Установка: `deploy/mirror-github.sh` → `/usr/local/bin/hackathon-mirror`,
`deploy/git-askpass.sh` → `/usr/local/bin/hackathon-git-askpass` (0555),
`deploy/hackathon-mirror.service` и `.timer` → systemd, затем
`systemctl enable --now hackathon-mirror.timer`. Токен передаётся только через
`GIT_ASKPASS` и не попадает в аргументы процесса, URL или репозиторий.

Локально remote уже добавлен: `git remote -v` показывает `github`. Первый push
выполняется после коммита: `git push github task/1-team-admin` (или
`git push github main`). Дальше ветки и теги синхронизируются таймером каждые
пять минут; удалённые ветки в GitHub удаляются (`--prune`).

## Конфигурация

Публичные адреса задаются только переменными `PUBLIC_BASE_URL` и
`PLANNER_BASE_URL`. Текущий домен: `https://cool-domain.online`, планировщик —
`https://planner.cool-domain.online`; DNS и TLS-сертификаты для обоих имён
должны указывать на первый сервер. Остальные ключи — в `.env.example`; секреты
живут в `/etc/hackathon/*.env` с правами 0600. Mihomo-конфигурация
`infra/mihomo/hackathon.yaml` направляет через VPN только `10.77.0.0/24`,
оставляя интернет и DNS прямыми; API отклоняет конфигурацию с приватным ключом.

## Проверки

Сервер: из `server` выполнить `go test ./...`, `go vet ./...`, `go build ./cmd/...`.
Это же покрывает агентов, воркер, оркестратор, генератор Mihomo и защиту GitLab:
они переписаны на Go и лежат в `server/internal/infra/*`, команды — в `server/cmd/*`.
Для интеграционного теста `TEST_DATABASE_URL` должен указывать на отдельную
пустую БД `portal_test`; тест выполняет up/down/up только в ней.

Клиент: `bun run check`, `bun run build:client`, `bun run typecheck:client`.
Контракт: `bun run gen:api`; расхождение `api/openapi.json` и
`client/src/shared/api/schema.d.ts` валит CI.

Браузерные проверки: `bun x playwright test`; API подменяется только внутри
тестов. Это проверка интерфейса, а не провайдера.

Агенты и воркер: `go test ./internal/infra/...`. Тесты не трогают реальные
VPN-профили и не требуют Docker. Бинари собираются командами
`go build ./cmd/ops-agent ./cmd/worker-agent ./cmd/orchestrator ./cmd/mihomo-gen ./cmd/protect-gitlab`.

Не проверяется локально без инфраструктуры: сборка Docker-образов, живое
развёртывание на двух серверах и реальные вызовы GitLab/Cloud.ru. Эти шаги
выполняются на серверах и в CI, а не выдаются за проверенные.
