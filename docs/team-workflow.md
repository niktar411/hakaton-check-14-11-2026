# Работа команды и общая доска

## Где хранить задачи

Предлагаемый вариант: Linear как общая доска, репозиторий — отдельно.
Официальный удалённый MCP: https://mcp.linear.app/mcp
Документация: https://linear.app/docs/mcp
Сервис ещё не подключён, проект и задачи в нём не созданы.

Подключение выполняется отдельно в каждом агентном клиенте под учётной записью
участника. Поддержка зависит от клиента, а не от названия модели Kimi/DeepSeek/Claude.
Если MCP недоступен, участник работает с той же карточкой через веб-интерфейс,
передаёт актуальный текст агенту и переносит отчёт обратно.
MCP даёт инструменты доступа; он сам не запускает агентов и не синхронизирует их мысли.

Не ведите вторую независимую доску в markdown. Карточка — источник статуса,
репозиторий — источник кода, контракта API и технических решений.
Если команда уже использует GitLab Issues, сначала оцените работу на его доске,
чтобы не вводить второй сервис без необходимости.

## Статусы и ответственность

| Статус | Значение | Кто переводит |
|---|---|---|
| Предложено | Идея, дефект или новая работа | Любой участник/агент |
| Готово к работе | Тимлид согласовал объём, критерии и владельца | Тимлид |
| В работе | Владелец начал, ветка указана в карточке | Владелец/его агент |
| Заблокировано | Есть конкретное препятствие и нужное решение | Владелец/его агент |
| На проверке | Есть результат, запрос слияния и отчёт | Владелец/его агент |
| Нужны исправления | Приёмка не пройдена, замечания перечислены | Тимлид |
| Готово | Проверки пройдены, результат принят и слит | Тимлид |
| Отклонено | Предложение не принято, причина записана | Тимлид |

Агент может сообщить, что задачу выполнить нельзя, и указать причину;
это блокировка, а не право отменить командную задачу.
Один человек отвечает за одну активную задачу. Назначение тимлидом снижает риск
двойного захвата; чтение и обновление карточки через MCP не гарантируют атомарного захвата.

## Что видит тимлид

На общей доске: владелец, приоритет, статус, блокировка, зависимости, ссылка на ветку
и запрос слияния. В комментариях — начало работы, существенная блокировка,
передача на проверку. Не нужно засорять карточку каждым вызовом инструмента.
Без отдельной автоматизации доска отражает последние опубликованные обновления,
а не непрерывную активность агента на компьютере участника.

## Разделение работ

Тимлид: контракт API, права доступа, миграции, сервер, инфраструктура, итоговое ревью.
Участники: небольшие страницы и компоненты, интеграция с согласованным API,
сценарии проверки и документация. Изменения общих компонентов согласуются заранее.
Задачи оценивайте по видимому результату; крупную функцию разбивайте на независимые части.

До параллельной работы соберите один сквозной сценарий: клиент → API → БД → ответ.
Затем зафиксируйте контракт, чтобы клиент и сервер не придумывали разные поля и пути.

## Проверки и приёмка

`bun run check` сейчас проверяет инструменты каркаса: линтер, slop-check, типы и тесты.
Он не доказывает работоспособность будущего приложения.
При появлении сервера обязательны его сборка, тесты, проверки прав и миграций;
при появлении клиента — сборка, тесты нужного сценария и проверка интерфейса.
Локальный pre-push полезен, но может быть отключён. Итоговые требования задайте
в CI на сервере репозитория и запретите прямую запись в основную ветку.

Шаблон карточки: `docs/task-template.md`.
